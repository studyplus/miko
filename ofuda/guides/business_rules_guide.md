# business_rules.md 生成指示書

機能のビジネスルールを `business_rules.md` として生成するための指示書。既存の実装からの逆引き（モード A）と、提案からの新規作成（モード B）の両方に対応する。

この文書は BR を書くたびに必要な核だけを持つ。以下は必要なときだけ読む:

- `.miko/guides/cross_category_guide.md` — 横断カテゴリ（`[横断]` マーク・`[xc:…]` タグ）の判定・書き方・書き込み時の検査（lint）
- `.miko/guides/implementation_mapping_guide.md` — 実装マッピングの書き方と表記規約

---

## 成果物の役割分担

| ファイル | 役割 |
|---|---|
| `miko/<capability>/business_rules.md` | ドメインの判断基準（なぜそうなっているか） |
| `miko/<capability>/high_level_design.md` | ケイパビリティの構造と全体像。技術選択の決定・意図・トレードオフ（ADR）は「設計上の特徴」に書く |
| `miko/<capability>/proposals/` | 変更の背景・動機、機能仕様、検討・却下した代替案などの経緯 |
| `miko/glossary.md` | 用語の定義。見出し語はシステム全体で一意にし、同じ語が別概念を指すなら別名を立てて分ける |

## ビジネスルールとは何か

**ビジネスルールとは、合理的な別の選択肢があったのに、ビジネスが選んだ判断のことである。** 「このビジネスでは何が真か」を記述するもので、「システムがどう振る舞うか」ではない。技術的に必然な制約（違反するとバグやデータ破壊が起きるもの）はビジネスルールではない。

| | ビジネスルール | 仕様 |
|---|---|---|
| **問い** | 「何が真か」 | 「どう振る舞うか」 |
| **例** | 未決済の注文は出荷できない | キャンセルボタンを押すと確認ダイアログを表示する |
| **実装が変わったら** | 変わらない | 変わりうる |
| **書く場所** | business_rules.md | proposal の機能仕様 / spec.md |

**迷ったときの判定**: 「実装技術や UI を変えても、この記述は変わらないか？」— Yes ならビジネスルール、No なら仕様。

**粒度の原則**: 提案や議論が詳細でも、BR の粒度は変わらない。UI や細かい仕様の話をしているときほど、このフィルタを強く意識する。通常の機能追加で新設 BR が 5 本を超えたら粒度が細かすぎる可能性が高い。

### 判定テスト

ルールを書く前に、以下で「ビジネスルールかどうか」を機械的に判定する。

**[制約] の判定: 「却下した代替案」テスト** — 合理的な代替案（別の選択肢）が書けるか？

- 書ける → ルールである。書く
- 代替案が「バグを作る」「データを壊す」「やらない」しかない → ルールではない。書かない

例: 「再付与は冪等にする」→ 代替案「エラーにする」→ **ルール**。「トランザクション内で作成する」→ 代替案はデータ不整合 → **ルールではない**。「送信者は 2 種類」→ 現実的な代替案なし → **ルールではない**

**[導出] の判定: 「ビジネス定義」テスト** — 技術的に必然ではなく、ビジネスが定義したマッピングか？ Yes なら書く。

**判定できない場合**: 「暗黙のルール（要確認）」として末尾に列挙し、人間に確認する。

コードに書いてあるかどうかは判断軸にならない（BR は最終的にコードで表現される）。問うべきは「別の選択肢がありえた中で選ばれたものか」であり、そうでなければ実装の写経である。

### よくあるアンチパターン

判定テストを通したつもりでも、以下は BR ではない。

1. **ユーザー要望の言い換え** — 「〜したい」をそのまま「〜できる」と書いたもの。要望の **背後にある条件・閾値・除外規則・対象範囲** だけが BR 候補
2. **実装トレース（UI 表示・通知・出力の「存在そのもの」）** — 「画面に X を表示する」「Y のときメールを送る」「Z を記録する」。表示する **条件**、送る **閾値**、対象から **除外する規則** が BR の本体

ただし、その背後に判断が乗っていれば BR。迷ったら「却下した代替案」テストに戻り、「やらない／別の条件にする」以外の合理的な代替案が書けるかを厳しく問う。

| 悪い例（書いてはいけない） | 良い例（こう書く） | 理由 |
|---|---|---|
| 「トライアル終了時に通知したい」→ トライアル終了時にメール通知を送る | トライアル終了の **3日前** に通知し、終了当日にも再送する | 送るかどうかではなく、**いつ・何回** が判断 |
| 管理者はオペレーター画面から注文をキャンセルできる | 管理者によるキャンセルは出荷後でも実行可能（一般ユーザーとの違い） | 操作の存在ではなく **ルールの違い** が BR |
| 未読通知のリマインドを送る | 通知発行から **24時間後** に未読のものをリマインド対象とする。**3回送ったら停止** | 条件と打ち切り規則が BR |
| キャンセル時に確認ダイアログを表示する | _(書かない)_ | 判断が乗っていない UI |
| キャンセルを記録する / レコードは論理削除する | 注文の監査証跡を保持するため、キャンセル後もレコードを残す | 「なぜ」が本当のルール |
| フレームワークのバリデーション構文で一意制約をかける | 1 ユーザーにつき、同一商品のレビューは 1 つしか投稿できない | フレームワーク非依存 |
| 処理中は**全チャネル**で受付不可 | 処理中は、対象チャネルだけでなく全チャネルで新規リクエストを受け付けない | 「全チャネル」は非自明な判断 |
| 定数定義でステータスを区別する / トランザクション内で同時に作成する | _(書かない)_ | 自明、または技術判断 |

### 書かないもの

上記アンチパターンに加えて:

- **自明なこと・一般的な技術知識から導けること・既存設計から推測できること**
- **実装方法**: どのクラス・メソッドで実現するか（実装マッピングに分離する）
- **UI 仕様・UI の表示状態の列挙**: 表示形式、レイアウト、色、文言、メール件名、「モーダルの状態は 10 種類」等。high_level_design.md か SDD の成果物に書く
- **技術仕様**: データフォーマット、CSV の列構成、エンコーディング、通信プロトコル

例外として、**出力内容そのものがビジネス判断であるもの**（「メールアドレスはマスクして表示する」「有償の利用者のみ集計に含める」）は BR に書く。その場合も書くのは判断だけで、画面の語彙は使わない（「ルール本文の語彙規律」参照）。

### 重要な代替案の記録

判定テストの過程で「これを知らないと将来間違えそう」な代替案を見つけたら、対応する proposal の「検討・却下した代替案」セクションに追記する。business_rules.md にはルールだけ簡潔に書く。

## ドメインビジネスルール / システムビジネスルール

**「紙運用」テスト**: そのルールは、システムが存在しない（紙台帳と人手だけで運用する）世界でも意味として成立するか？

| | ドメインビジネスルール（2.1） | システムビジネスルール（2.2） |
|---|---|---|
| **判定** | Yes（紙運用でも成り立つ） | No（システム前提の概念に依存する） |
| **例** | 出荷後はキャンセル不可 / 猶予期間は 24 時間 | 再付与は冪等にする / 応答失敗時は非同期リトライで整合性回復 |
| **典型語** | 期限・閾値・権限・対象範囲・除外規則 | 非同期・リトライ・冪等性・ロック・整合性回復 |

- コードの表現を一旦剥がしてから判定する。「自動キャンセル」「即時反映」は紙運用なら「日次でキャンセル」「翌朝確認」と置き換えられるのでドメイン。「非同期で整合性を回復する」「冪等に処理する」は紙運用に対応する概念がないのでシステム
- **1 ルールに混在させない**。ドメイン判断とシステム判断が混ざっていたら 2 ルールに分解し、それぞれのセクションのカテゴリに置く
- 各カテゴリは 2.1 / 2.2 のどちらか一方に置く。混じるカテゴリは分割を検討する

## ルール本文の語彙規律

本文の合否は**読者テスト**で判定する: コードを読んだことのないドメインエキスパートが、この文を理解できるか？ — No なら内容ではなく語彙の問題。ルール本文はビジネスの言葉、実装マッピングはコードの言葉。レイヤーを混ぜない。

技術用語を使ってよいかは「**実装を別技術に置き換えても、その語は残るか**」で判定する。残らない語は実現手段の名前、残る語は外から観測できる約束である。

| 語彙 | ルール本文での扱い | 行き先 |
|---|---|---|
| クラス名・メソッド名・ジョブ名・変数名 | **禁止**。ドメイン概念の言葉で言い換える | 実装マッピング |
| 実現手段の固有名（Job、enqueue、コールバック、トランザクション等） | **禁止**。別技術に置き換えても残る言葉で書く | 実装マッピング |
| 振る舞いの意味論を表す技術用語（非同期、リトライ、ロールバック、冪等等） | **可**。曖昧な日常語（「自動で」等）に言い換えて精度を落とさない。一般に通じにくい語は glossary で定義 | — |
| API のパラメータ名・レスポンスのフィールド名 | **禁止**。ビジネス語で書く | 実装マッピング |
| テーブル名・カラム名 | **可**。ドメイン概念の識別子として使ってよい | — |
| マスター値・enum 値・センチネル値の生値 | **原則禁止**。glossary か状態遷移で対訳を定義したビジネス用語で書く。初出に限り「ビジネス用語（値）」の併記可 | 対訳は glossary.md / 状態遷移、生値は実装マッピング |
| 閾値・期限・件数上限などの数値 | **書く**。これこそ BR の本体 | — |
| 他のケイパビリティでは別概念を指す語 | **禁止**。glossary で立てた一意な別名で書く（「確定」ではなく「決済確定」） | glossary.md |
| 画面名・パネル位置・列構成・ボタン・文言・件名 | **禁止**。表示・出力に判断が乗っている場合も書くのは判断だけ | 機能仕様 / HLD |

| 悪い例 | 良い例 |
|---|---|
| `UserCoupon` を持つユーザーはアカウント統合できない | クーポンの紐づけを持つユーザーは統合できない |
| ステータスが `inviting` または `active` であれば `granted` と判定する | 招待中または利用中であれば、権限は付与済みと定義する |
| Job が再実行された場合、例外を発生させて中断する | 完了済みの処理の再実行はエラーとして中断する（黙って成功扱いにしない） |
| 入力された ID リストは受付時に重複を排除する（`.uniq`） | 同じ対象が重複指定された場合は 1 件として扱う |
| 停止中の利用者は集計バーの分母から除外するが、右パネルのカード表示は維持する | 停止中の利用者は集計の分母から除外する。ただし停止前の記録の参照は維持する |

## 1 ルールの粒度と長さ

1 つのルールは 1 つの判断（「却下した代替案」テストを 1 回通せる単位）を表し、本文はそれを言い切る最小限の長さにする。文の数に固定の上限はない。次のどちらかに当たったら「詰め込みすぎ」の黄信号:

- **本文がおおむね 150 字を超える**: 経緯・理由・仕様が紛れ込んでいる可能性が高い
- **独立した判断が 3 つ以上並んでいる**（補足を 1 つ足した 2 判断までは許容。例: 「自動再連携しない。再招待は手動運用とする」）

黄信号が出たら、**分解**（別のルール ID に割る）/ **経緯を落とす**（理由・却下した代替案は書かず結論だけ残す）/ **仕様を除外**（UI・通知・出力の手順は機能仕様・HLD へ）のいずれかで対処する。150 字はハード上限ではなく再点検の合図であり、意味を切り詰めたり 1 つの判断を不自然に割ったりするための数値ではない。

## ビジネスポリシー（ビジネス方針）

**ビジネスポリシーとは、ケイパビリティに通底する価値判断・指針である。** コードから抽出したルールに埋もれがちな価値判断を明文化して分離する層。ポリシーとルールは **整合する関係** であって、上下の導出関係ではない（ルールが先にあり、後から方針が見えてくることもある）。

**「客観性」テスト**: その候補は、任意のケースで客観的に判定できるか？

- Yes（条件・閾値・対象が明確）→ **ルール**。例: 「キャンセル猶予期間は確定から 24 時間」「キャンセル後もレコードを 3 年保持する」
- No（ケースごとに人間の解釈が要る価値判断・優先順位）→ **ポリシー**。例: 「ユーザーの予期せぬ損失を防ぐことを優先する」「監査証跡を保持する」

書き方:

- `## ビジネスポリシー（ビジネス方針）` セクションに `POL-{連番}` で列挙し、末尾に `<!-- last: POL-XX -->` で最終採番を記録する
- 1 ポリシー = 1 つの価値判断。短く言い切る。ケイパビリティあたり 3〜5 個が目安
- **閾値や具体条件を書かない**（客観的に判定できるならルール）
- ルールとの対応は機械的なリンクで管理しない。強調したい場合はルール本文で散文的に言及する（例: 「監査証跡（POL-02）の方針に従い、…」）
- **ルールのまとめ書き**（「キャンセルの条件を明確にする」等）や、**どの事業にも当てはまる価値観**（「ユーザーを大事にする」等）はポリシーにしない

## ドキュメント構造

```
# {ケイパビリティ名} ビジネスルール

## 背景
## ビジネスポリシー（ビジネス方針）
## 状態遷移（該当する場合）
## 1. 操作の定義（Operations）
## 2. ビジネスルール・カタログ
### 2.1 ドメインビジネスルール
### 2.2 システムビジネスルール
## 3. 関連ケイパビリティとの境界
```

**既存 BR の扱い:** この構造は新規ケイパビリティ向け。既存の `business_rules.md` は、ユーザーから明示的な移行依頼がない限り、**ファイル構造**（ポリシーセクションの新設、2.1/2.2 への分割等）と **proposal が触らない既存ルールの本文**には手を入れない（文字数・語彙規律など現在基準への合わせ込みもしない）。**改訂・新設するルール** の本文だけに現在基準を適用する。

**各セクション:**

- **背景**: なぜこの機能が必要になったか。ビジネス上の課題。2〜3 段落以内
- **状態遷移**: 状態を持つ概念がある場合のみ。Mermaid の stateDiagram-v2 で図示し、遷移表で条件を補足する
- **操作の定義**: 全操作をアクター/トリガー別にグループ化して列挙する（フラットなリストにしない）
  ```markdown
  ### オペレーター操作（API）
  - **紐づけ** — 説明。`POST /api/...`
  ### イベント駆動の自動同期
  - **料金プラン変更** — 説明。
  ### 外部連携（外部サービス名）
  - **AI権限の付与・剥奪** — 説明。
  ### バッチ処理
  - **トライアル終了処理** — 説明。
  ```
- **境界**: 他ケイパビリティとのビジネス上の責務分担を「借りているもの」「渡しているもの」「境界の注意点」の 3 軸で書く。相手を列挙できる二者間の依存はここで扱う。横断カテゴリへの依存はここに書かない（ルールの `[xc:…]` タグが唯一の置き場）

### カタログの書き方

- **カテゴリ**: 関連するルールをグループ化する。名前は短い日本語 + 英字プレフィックス（例: `#### 権限管理（PERM）`）。カテゴリは既定で自由に分割・改名・統合してよい。`[横断]` マーク付きのカテゴリだけは改名等が契約変更になる（`cross_category_guide.md` 参照）
- **ルール ID**: `{プレフィックス}-{連番}`。削除したルールの番号は欠番にする（harae.md や proposal が ID で参照しているため振り直さない）。カテゴリ末尾に `<!-- last: PREF-03 -->` で最終採番を記録する
- **タグ**: **[制約]**（〜でなければならない / 〜は禁止。違反したらエラー）、**[導出]**（A ならば B と定義する。事実から値や状態が決まる）。迷ったらどちらかに寄せる。タグの厳密さよりルールの内容が重要
- **実装マッピング**: ルール本体と分離し、`<details><summary>実装マッピング</summary>` で折りたたむ。既存実装から生成する場合のみ記載し、提案段階では空でよい。書式は `implementation_mapping_guide.md` に従う

```markdown
#### 権限管理（PERM）

**ルール:**
- **PERM-01** [制約] AI質問機能を利用するには、有効な権限が存在しなければならない。

<details><summary>実装マッピング</summary>

- PERM-01 → `XxxConcern#method` / 説明

</details>
<!-- last: PERM-01 -->
```

## 生成モード別の手順

### モード A: 既存の実装から生成する場合

1. 対象のコード（コントローラ、モデル、ジョブ、フォーム、ポリシー）を読み、**コードの書き方ではなく、その背後にあるビジネス判断**を抽出する
2. 本文を語彙規律で検査する（クラス名・メソッド名・enum の生値が漏れやすい）
3. 「客観性」テストでポリシー（`POL`）を分離し、「紙運用」テストで 2.1 / 2.2 に振り分ける
4. 実装マッピングを `<details>` 内に記載する
5. コードに暗黙的に埋め込まれているが明文化されていないルール・ポリシーを「暗黙のルール（要確認）」として末尾に列挙する
6. `grep -n 'cross-category' miko/*/business_rules.md` がヒットしたら `cross_category_guide.md` を読み、概念の効果を実装しているルールに `[xc:…]` タグを付ける

### モード B: 提案から生成する場合

提案に書かれた詳細な仕様は BR には書かない。

1. 提案の要件をルール単位に分解する
2. 「客観性」テストでポリシー候補とルール候補を分け、「紙運用」テストで 2.1 / 2.2 に振り分ける
3. 提案に明示されていないが論理的に必要なルール・ポリシーを推論し「暗黙のルール（要確認）」として末尾に列挙する
4. 技術選択が含まれる場合、high_level_design.md の「設計上の特徴」への追記を検討する
5. 他ケイパビリティの操作の可否・意味を変える状態・属性が含まれる場合は、`cross_category_guide.md` の判定テストを適用し、満たすものを横断カテゴリの昇格候補としてユーザーに提示する（宣言は proposal を通す）
