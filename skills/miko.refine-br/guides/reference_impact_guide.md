# ルール ID 参照調査ガイド

このファイルは、分割・統合の対象ルール ID を参照している箇所を洗い出し、旧 ID → 新 ID の対応表の下書きを作る手順書である。この内容に正確に従うこと。

あなたは会話の文脈を持たない調査役である。渡されたルール ID と分割・統合案、そしてリポジトリ内のファイルだけを材料に調査する。

## 前提

呼び出し元から以下が渡される:
- ケイパビリティ名
- 対象ルール ID の一覧
- 分割・統合の案（分割後の本文と新 ID 案、または統合先 ID）

## 目的

**対応表を確定させることではない。** 機械的に決まる行と、人間が決めなければならない行を分けることが目的である。曖昧なものを埋めて表を完成させてはならない。

読み込むファイル:
- `miko/<capability>/harae.md`（あれば）
- `miko/<capability>/proposals/*.md`（あれば）
- `miko/<capability>/business_rules.md` — 対象ルールの現在の本文の確認用

これ以外（プロジェクトのコード、他ケイパビリティのファイル）は読まない。

---

## 手順

### 1. harae.md の参照を列挙

`harae.md` の指摘一覧と詳細を読み、「関連ルール」に対象ルール ID を含む指摘を **全ステータス** について列挙する。

指摘ごとに以下を記録する:
- 指摘番号、ステータス（open / resolved / dismissed / obsolete）、検証軸
- 指摘・詳細・対処案・解決の本文が、対象ルールの **どの部分**（どのサブ条件・どの側面）に言及しているか

open の指摘は生きている指摘であり、対応付けを誤ると検証履歴が失われる。resolved / dismissed も、後から経緯を辿る材料として参照は保つ。

### 2. proposals の参照を列挙

`miko/<capability>/proposals/` 配下を Grep し、対象ルール ID を参照している proposal を列挙する。

proposal ごとに以下を記録する:
- ファイルパス
- 参照箇所のセクション（ビジネスルールの変更 / 影響範囲 / 検討・却下した代替案 / 祓え検証 等）
- そのルールの **どの部分** を論点にしていたか

### 3. 対応表の下書き

分割案の各新 ID に対して、ステップ 1・2 で列挙した参照がどちらに対応するかの下書きを作る。

- 参照の本文が、分割後のどちらの判断について書かれているかがテキストから一意に読み取れる場合のみ、対応先を書く
- 読み取れない場合は対応先を空欄にし、次のステップの曖昧サインを付ける

### 4. 曖昧サインの検出

以下のいずれかに該当する参照には、必ず曖昧サインを付ける。**該当したら対応先を推測で埋めない。**

| サイン | 内容 |
|---|---|
| **部分参照** | 指摘・proposal が、ルール本文の一部（サブ条件・特定の側面）だけを指して書かれている。分割後にどちらの新 ID に付くかが本文だけでは決まらない |
| **独立性が論点** | 指摘が「そのルールが独立した ID として存在すること自体」を論点にしている。統合するとその指摘の前提が壊れる |
| **参照過多** | 1 つの旧 ID に対する参照が、harae 指摘と proposal を合わせて 5 件以上ある。参照が多いルールほど分割時の対応付け精度が落ちる |

同一ルールの複数の側面（定義部分と運用時の挙動部分）が別々に参照されている場合は、**部分参照** として扱う。

---

## 出力形式

以下だけを返す。調査結果以外（感想、次の手の提案、会話文）は返さない。

```
## 対象: {旧ルールID}

- **参照件数**: harae {n} 件 / proposal {m} 件
- **曖昧サイン**: なし / 部分参照 / 独立性が論点 / 参照過多（複数該当ならすべて列挙）

### 参照一覧

| 参照元 | ステータス | 参照している部分 | 対応先（下書き） | 曖昧サイン |
|---|---|---|---|---|
| harae #3 | open | 猶予期間の判定部分 | {新ID} | なし |
| proposals/2026-03-08-xxx.md（ビジネスルールの変更） | — | ルール全体 | 要確認 | 部分参照 |

### 要確認の理由

- harae #7: {なぜ機械的に決まらないか。1〜2文} 
```

- 参照が 0 件の場合も「参照なし」と明示する
- 対応先が決まらない行は `要確認` と書き、推測した ID を書かない
