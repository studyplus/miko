## 入力

```text
$ARGUMENTS
```

入力の形式: `<capability_name> [開始フェーズ]`

- 例: `/miko.refine-br order_management`（フェーズ A から順に）
- 例: `/miko.refine-br order_management C`（フェーズ C から再開）
- 開始フェーズは `A` / `B` / `C` / `D` のいずれか。省略時は `A`
- 空の場合はエラー: 「⛩️  ケイパビリティ名をお願いいたします（例: `/miko.refine-br order_management`）」

**`miko/<capability>/business_rules.md` が存在しない場合はエラー:**

> ⛩️  `miko/<capability>/business_rules.md` が見つかりません。
> 既存コードがある場合は `/miko.catchup <capability>`、新規ケイパビリティの場合は `/miko.new-cap <capability>` で先に business_rules.md をお作りくださいませ。

## このスキルの役割

既存の `business_rules.md` をリファクタリングする。ここでのリファクタリングとは、**ドメインの判断を変えない書き直しと再配置** である。

`.miko/guides/business_rules_guide.md` は「既存 `business_rules.md` の構造と、proposal が触らない既存ルールの本文には、ユーザーからの明示的な移行依頼がない限り手を入れない」と定めている。**このスキルの実行が、その明示的な移行依頼にあたる。**

### 判断が変わる変更は扱わない

| 変更の性質 | 担当 |
|---|---|
| 判断を変えない書き直し・再配置（語彙・粒度・構造・配置） | **このスキル** |
| 判断そのものの変更（ルールの新設、条件・閾値・対象範囲の変更、廃止） | `/miko.propose` |
| 実装とルールの乖離（未実装なのに制約と断定している、既知の実装漏れがルールとして残っている） | `/miko.propose`（このスキルは検出して報告するだけ） |

本文から判断が消える変更（ルールごとの削除、対象範囲の縮小、閾値の変更）は、見た目が「本文の整理」であってもこのスキルでは行わない。検出して完了報告に回す。

### フェーズ構成

| フェーズ | やること | ルール ID | 適用の仕方 |
|---|---|---|---|
| **A** | フォーマット最新化（ポリシーセクション新設、2.1/2.2 分割、採番コメント） | 不変 | 確認の上で適用 |
| **B** | 安全な言い換え（語彙規律違反、経緯の混入、実装トレース・ADR 混入） | 不変 | 1 ルールずつ確認して適用 |
| **C** | 分割・統合の提案（新規 ID 採番を伴うもの） | **変わる** | 対応表を人間が決めた上で適用、または proposal に書き出す |
| **D** | ケイパビリティ横断チェック（境界・重複・同音異義語・帰属） | 不変 | **検出のみ。修正しない** |
| **記録** | 適用を proposal として残す（本文が動いた場合・ID が動いた場合） | — | 確認の上で生成 |

各フェーズの末尾に確認ゲートを置く。**どのゲートでも打ち切ってよい。** 全フェーズを 1 回で通す必要はない。

### 保証すること

- フェーズ A・B・D はルール ID を一切変更しない。`harae.md` と `proposals/` からの ID 参照は壊れない
- フェーズ C だけが ID を動かす。ID を動かす前に、参照元（`harae.md` の指摘・`proposals/`）の対応付けを **必ず人間に決めてもらう**。対応表を機械的に確定させて適用することはしない
- ルールの判断（条件・閾値・対象範囲・除外規則）は、どのフェーズでも変えない
- **本文から落とした情報は捨てない。** 経緯・却下した代替案・ADR は、proposal か `high_level_design.md` のどちらかに移す（後述の「適用記録の proposal」）

### 適用も記録に残す

miko の原則では proposal がケイパビリティの変更履歴になる。判断を変えないリファクタリングであっても、**本文が書き換わった場合と ID が動いた場合は記録を残す**。

| フェーズ | 記録 |
|---|---|
| A のみ（構造だけを動かした） | 任意。残すかどうかをゲートで確認する（本文も ID も変わっていないため） |
| B（本文を書き換えた） | **必須**。本文から落とした経緯・却下した代替案の移設先になる |
| C の (a) ルート（このスキルが適用した） | **必須**。旧 ID の欠番の由来と対応表の記録になる |
| C の (b) ルート | 適用前の proposal がそのまま記録になる（別ファイル） |
| D のみ | 不要（BR を変更していない） |

### フェーズ間の再開

このスキルは進捗の状態ファイルを持たない。ゲートで打ち切った場合は、開始フェーズを指定して再実行する（`/miko.refine-br <capability> C`）。フェーズ A の成果はファイルの構造に残るため、再実行時の診断で「済」と判定される。フェーズ B 以降は毎回検出をやり直すが、既に直した箇所は検出されないため重複した提示にはならない。

## 手順

### 0. 入力検証と資料の読み込み

`$ARGUMENTS` の先頭ワードをケイパビリティ名としてスネークケースに正規化する。2 番目のワードがあれば開始フェーズとして解釈する（`A`〜`D` 以外なら開始フェーズなしとして扱い、`A` から始める）。

以下を読み込む。

**指示書（必須）:**
- `.miko/guides/business_rules_guide.md` — ドキュメント構造、客観性テスト、紙運用テスト、語彙規律、粒度基準、カタログの書き方
- `.miko/guides/tone_guide.md` — 対話スタイル。**このファイルの口調・絵文字・出力言語ルールに従うこと**

**実例（目標とする構造）:**
- `.miko/examples/business_rules.md`

**対象:**
- `miko/<capability>/business_rules.md` — 全文
- `miko/<capability>/high_level_design.md` — あれば（ADR の移設先の確認用）
- `miko/<capability>/harae.md` — あれば（フェーズ B・C で参照する指摘）
- `miko/<capability>/proposals/` — ファイル名一覧（フェーズ C で参照を辿る起点）
- `miko/glossary.md` — あれば（マスター値の対訳、用語衝突の確認用）

### 1. 現状診断

対象ファイルを診断し、フェーズごとの作業量を提示する。

| 項目 | 判定 |
|---|---|
| ビジネスポリシーセクション | 有 / 無 |
| 2.1 / 2.2 分割 | 済 / 未 |
| 状態遷移セクション | 有 / 不要 / 無（状態を持つ概念あり） |
| 各カテゴリの `<!-- last: -->` | カテゴリごとに 有 / 無 |
| ルール総数・カテゴリ数 | 数値 |

診断結果と、これから通すフェーズを提示してから作業に入る。開始フェーズが指定されている場合は、そのフェーズに関わる項目だけを報告し、指定されたフェーズから始める（前のフェーズは実行しない）。

**フェーズ A の対象がすべて揃っている場合**: フェーズ A は「対応不要」として報告し、フェーズ B へ進むかを確認する。

## フェーズ A: フォーマット最新化

ルール ID・本文・タグを変えずに、ファイルの構造を現行ガイドの `## ドキュメント構造` に揃える。

### A-1. ドメイン / システムの判定（2.1 / 2.2 が未分割の場合）

`business_rules_guide.md` の「紙運用」テスト（そのルールは、システムが存在しない世界でも意味として成立するか）をカタログの全ルールに適用する。

**判定は、ルール本文に書かれている内容だけを見て行う。** 背景セクション・実装マッピング・proposal に書かれた「なぜこのルールが必要になったか」という理由は判定に使わない。ルールが生まれた理由が技術的（非同期処理、外部システムとの整合性回復など）であっても、ルールの中身が紙運用で成立するなら、それはドメインビジネスルールである。

- 良い判定: 「投稿者名は正規の経路以外からは参照されないよう秘匿する」— 実現手段が暗号化であっても、「誰に開示するか」という約束自体は紙の鍵付き書庫でも成立する → ドメイン
- 避けるべき誤り: 実装マッピングに「平文を残さないため」と書かれていることを根拠に、上記をシステム側へ分類すること。**ルールが必要になった理由（why）と、ルールの中身の分類（what）を混同しない**

**カテゴリ単位で判定する:**
- カテゴリ内の全ルールが同じ判定に収まる場合、カテゴリごと 2.1 または 2.2 に配置する
- 混在する場合は、ガイドの原則（同一カテゴリはどちらか一方に置く）に従い、カテゴリを 2.1 側・2.2 側に分けて両方に配置する。**プレフィックスも番号も変えない。** カテゴリ見出しは両側で同じ日本語名・同じプレフィックスを使う（`#### 申込管理（APP）` が 2.1 と 2.2 の双方に現れてよい）

**要確認の扱い:** 本文の内容だけを見ても判定が割れるルールは、自動で決めずに「要確認」として挙げ、A-4 で個別に判断を仰ぐ。両論を意図的に作り出さない。実データでは、本当に割れるのはケイパビリティあたり数件に収まる。

### A-2. ビジネスポリシー候補の検出（ポリシーセクションが無い場合）

`business_rules_guide.md` の「客観性」テスト（任意のケースで客観的に判定できるか。できないなら方針）を、背景セクションの記述と各ルールの前提になっている考え方に適用する。

- 価値判断・優先順位の表明が既存ルールや背景に埋没しているものを `POL-{連番}` の候補として抽出する
- **無理に見つけない。** 目安はケイパビリティあたり 3〜5 個。候補が薄い場合は、セクション新設を今回は見送るかどうかを A-4 で確認する
- ポリシー候補の抽出元（どのルール・どの背景記述から読み取ったか）を必ず併記する。抽出元のルール本文は変更しない（ポリシーはルールの上位ではなく、整合する別の層である）

### A-3. 状態遷移セクションの欠如（状態を持つ概念がある場合）

状態を持つ概念があるのに状態遷移セクションがない場合、内部矛盾の検証指摘を繰り返し生む原因になる。以下の条件でのみ下書きを提示する。

- 図示する遷移は、**既存のルール本文・操作の定義・glossary の対訳から読み取れるものだけ**にする。読み取れない遷移を推測で足さない
- 読み取れない遷移・条件は、図に含めず「要確認」として列挙する（空欄のまま人間に渡す）
- 状態名は生値ではなく `business_rules_guide.md` の語彙規律に従い「ビジネス用語（値）」の併記で書く

下書きを作らずに「欠如を報告するだけ」に留める選択も提示する。

### A-4. 【確認 A】適用案の提示

以下をまとめて提示し、承認を得る。

- 2.1 / 2.2 の配置案（カテゴリ単位の判定結果、混在カテゴリの分割方針）
- 要確認ルールの一覧。**「A（ドメイン）と B（システム）どちらの解釈も成り立ちますが、どちらに寄せますか」の形で 1 件ずつ**判断を仰ぐ。まとめて一括承認を求めない
- ビジネスポリシー新設案（候補と抽出元、または「候補なし」）
- 状態遷移の下書き（作った場合）と、その要確認箇所
- `<!-- last: -->` の追加箇所

フィードバックがあれば反映して再提示する。

### A-5. 適用

- ルール ID・タグ・本文・実装マッピングは一切変更しない
- カテゴリ内のルールの記述順は元のまま保つ
- ビジネスポリシーセクションは「背景」の直後、「状態遷移」（あれば）の前に置き、末尾に `<!-- last: POL-XX -->` を付ける
- 2.1 / 2.2 に配置し直した後、各カテゴリ（分割された場合は分割後のそれぞれ）の末尾に、そのカテゴリの最終 ID で `<!-- last: -->` を付ける

### A-6. 【ゲート A】

変更内容（構造の差分のみ）を報告し、フェーズ B に進むか、ここで打ち切るかを確認する。打ち切る場合は「適用記録の proposal」→「完了報告」へ進む。

## フェーズ B: 安全な言い換え

ルール ID を変えずに、本文の書きっぷりを現行基準に合わせる。**判断は変えない。**

### B-1. 禊による本文審査（サブエージェント）

カタログの既存ルール本文を、`.miko/guides/misogi_guide.md` の審査役に掛ける。起草者ではない審査役にテキストだけで判定させるため、サブエージェント（Agent ツール）を起動する。

サブエージェントに渡す情報:
- `.miko/guides/misogi_guide.md` のパス — 「このファイルを読み、指示に正確に従え」と指示する
- ケイパビリティ名
- 審査対象のルール本文（ルール ID と `[制約]`/`[導出]` タグ付き）

**会話の経緯・ユーザーの発言・背景セクション・実装マッピングは渡さない。** 文脈が審査を汚染する。特に「なぜこのルールが必要になったか」を渡すと、語彙・粒度の判定がその理由に引きずられる。

ルールが 30 本を超える場合はカテゴリ単位でグループ分けし、サブエージェントを並列で起動する。

### B-2. 審査結果の裁定

審査結果をこのスキルのスコープに振り分ける。

| 違反種別 | このスキルでの扱い |
|---|---|
| 語彙逸脱（クラス名・メソッド名・API パラメータ名・enum の生値・実現手段の固有名） | **フェーズ B**: 書き換え案を提示 |
| 粒度過大のうち、経緯・理由の記述を落とせば収まるもの | **フェーズ B**: 経緯を落とした本文案を提示（結論だけ残す）。**落とす経緯は控えて適用記録の proposal に移す** |
| 粒度過大のうち、独立した判断が同居しているもの | **フェーズ C** の分解候補へ送る |
| 実装トレース / UI 仕様 / 技術仕様の**混入**（除いてもルールに判断が残る） | **フェーズ B**: 混入部分の除去案を提示。UI の表示状態の列挙・データフォーマット等は `high_level_design.md` への移設候補として示す |
| 実装トレース等が**ルールの全体**（除くとルールが消える） | **扱わない**。ルールごとの削除は判断の変更にあたる。完了報告で `/miko.propose` に誘導 |
| 要望の言い換え / 判定テスト不合格 | **扱わない**。同上 |
| 判定不能 | **扱わない**。完了報告で列挙 |

**語彙の言い換え先:**
- enum の生値・マスター値は `glossary.md` か状態遷移セクションの対訳を使う。対訳がない場合は言い換えを確定させず、要確認として提示する（glossary への追加は `/miko.propose` の領分）
- 他ケイパビリティで別概念を指す語は、glossary で立てた一意な別名に置き換える。別名がまだない場合は要確認として提示する
- 実装マッピングに書くべき語（クラス名等）が本文から消える場合、実装マッピングに同等の記載があるかを確認する。無ければ実装マッピングへの追記も併せて提案する

### B-3. ADR 混入の検出（メインセッション）

技術選定の決定・意図・トレードオフの議論がルール本文や実装マッピングに埋め込まれていないかを確認する。該当する場合は、`high_level_design.md` の「設計上の特徴」への移設案として提示する（`business_rules_guide.md` の注記に従い、ADR は BR に書かない）。

`high_level_design.md` が存在しない場合は、移設先がないため BR からの除去は行わず、検出の報告に留める。

### B-4. 【確認 B】1 ルールずつの差分提示

**一括適用はしない。** ルール 1 本ごとに以下を提示し、承認・修正・見送りを選んでもらう。

```
### {ルールID}

- 現在: {現在の本文}
- 案: {書き換え後の本文}
- 直した点: 語彙逸脱（`Xxx#method` → 業務語）/ 経緯の除去 / 仕様の除外
- 判断の変化: なし（条件・閾値・対象範囲・除外規則は同一）
```

「判断の変化: なし」と言えない案は提示しない。判断が動くなら `/miko.propose` の領分である。

件数が多い場合はカテゴリ単位で区切って提示してよいが、承認は 1 ルールずつ受け取る。

### B-5. 適用

承認された分だけ本文を書き換える。ID・タグは変えない。ADR の移設が承認された場合は `high_level_design.md` の「設計上の特徴」に追記する。

**落とした経緯を控える:** 本文から除いた経緯・理由・却下した代替案は、その場で破棄せずルール ID ごとに控えておく。「適用記録の proposal」に移す（ガイドは経緯を proposal に書くと定めており、本文から落とすだけでは行き先がなくなる）。

### B-6. 【ゲート B】

適用件数・見送り件数を報告し、フェーズ C に進むか打ち切るかを確認する。フェーズ C に送った分解候補があれば、その件数も伝える。打ち切る場合は「適用記録の proposal」へ進む。

## フェーズ C: 分割・統合の提案

新規 ID の採番を伴う変更を扱う。**このフェーズだけがルール ID を動かす。**

### C-1. 候補の確定

- フェーズ B から送られた分解候補（独立した判断が同居しており、経緯を落としても解けないもの）
- 1 ファイル内で同じ判断が複数の ID に分かれている統合候補

いずれも「判断の中身は変えず、境界を引き直すだけ」であることを確認する。分割の結果としてどちらかの判断が変わるなら、それは `/miko.propose` の領分として外す。

### C-2. 参照調査（サブエージェント）

対象ルール ID を参照している `harae.md` の指摘と `proposals/` を洗い出し、対応表の下書きを作る。サブエージェント（Agent ツール）を起動する。

サブエージェントに渡す情報:
- `.claude/skills/miko.refine-br/guides/reference_impact_guide.md` のパス — 「このファイルを読み、指示に正確に従え」と指示する
- ケイパビリティ名
- 対象ルール ID の一覧と、分割・統合の案（新 ID 案を含む）

対象ルールが多い場合は ID をグループ分けして並列に起動する。

### C-3. 適用ルートの判定

サブエージェントの結果に基づき、候補ごとにルートを決める。

**曖昧サイン**（`reference_impact_guide.md` が検出する）:
1. 指摘が本文の一部（サブ条件・特定の側面）だけを参照している
2. 指摘が「そのルールが独立 ID として存在すること自体」を論点にしている（統合すると指摘の前提が壊れる）
3. 1 つの旧 ID に対する参照が harae 指摘・proposal 合わせて 5 件以上ある

| 条件 | ルート |
|---|---|
| 曖昧サインなし、かつ参照が 0〜1 件 | **(a) このスキルが適用する** |
| 曖昧サインなし、参照が 2〜4 件 | **(b) proposal に書き出す** |
| 曖昧サインあり | **(b) proposal に書き出す**。対応表は自動生成せず、C-4 で 1 件ずつ人間に決めてもらう |

### C-4. 【確認 C】変更案と対応表の提示

候補ごとに以下を提示する。

- 分割・統合の案（分割後の本文、新 ID 案。統合の場合は統合先 ID と欠番になる旧 ID）
- 参照元の一覧（`harae.md` の指摘番号とステータス、proposal のパス）
- 対応表の下書き（旧 ID → 新 ID）
- 曖昧サインに該当した行は「この対応は主さまが個別にお決めください」と明示し、**1 件ずつ** 判断を仰ぐ。機械的に埋めた表を承認させない
- 判定ルート（(a) / (b)）とその理由

決められない行は「保留」として残してよい。保留がある候補は (b) ルートに回し、proposal 上に `要確認` として残す。

### C-5. (a) ルートの適用

- 分割: 旧 ID を欠番にし、新 ID を採番する（`<!-- last: -->` を更新）。番号は詰めない
- 統合: 統合先 ID に本文を寄せ、統合された旧 ID を欠番にする
- `harae.md`（生きている指摘）: 「関連ルール」欄の ID を、確認済みの対応表どおりに書き換える。指摘の本文・ステータスは変えない
- `proposals/`（変更履歴）: **旧 ID は消さず、新 ID を併記する**（`ORD-04` → `ORD-04（現 ORD-12 / ORD-13）`）。proposal は「そのとき何を決めたか」の記録なので、当時の ID を残したまま参照が辿れる形にする。本文の判断記述は変えない

書き換えた箇所を一覧で提示し、確認を取ってから保存する。**確認済みの対応表は「適用記録の proposal」に必ず載せる**（旧 ID がなぜ欠番になったかを後から辿れるようにするため）。

### C-6. (b) ルートの proposal 書き出し

`miko/<capability>/proposals/YYYY-MM-DD-refine-<kebab-case-title>.md` を生成する。これは **適用前** の proposal であり、後述の「適用記録の proposal」とは別のファイルにする（適用済みのものと未適用のものを 1 本に混ぜない）。構造は `.miko/examples/proposal.md` に従い、以下を明記する。

- **背景・動機**: リファクタリング（判断は変えない）であること、`/miko.refine-br` のフェーズ C で検出した経緯
- **ビジネスルールの変更**: 分割後の新設ルール、統合先の改訂、旧 ID の廃止。本文は判断を変えずに書く
- **影響範囲**: 「変更しないもの」に判断（条件・閾値・対象範囲）が同一である旨を書く
- **参照の付け替え**: 確認済みの対応表（旧 ID → 新 ID）を表で載せる。保留行は `要確認` と明記し、実装前に決める必要があることを書く。`harae.md` は ID を置き換え、`proposals/` は旧 ID に新 ID を併記する方針も書き添える

生成後の案内:

> ⛩️  proposal をお納めいたしました。
> `/miko.harae <capability> <proposal>` でルール体系を検証してから、`/miko.quick-impl <proposal>` で反映くださいませ。

### C-7. 【ゲート C】

(a) で適用した件数、(b) で書き出した proposal、保留にした対応表の行数を報告し、フェーズ D に進むか打ち切るかを確認する。打ち切る場合は「適用記録の proposal」へ進む。

## フェーズ D: ケイパビリティ横断チェック

**検出のみ。修正はしない。** 修正の是非そのものが人間のドメイン判断を要する。

### D-1. 調査（サブエージェント）

- `.claude/skills/miko.refine-br/guides/cross_capability_check_guide.md` のパス — 「このファイルを読み、指示に正確に従え」と指示する
- 対象ケイパビリティ名
- 調査を担当する他ケイパビリティ名の一覧

**会話の経緯・ユーザーの発言は渡さない。** ガイドのパスと調査対象の指定だけを渡す。

### D-2. 結果の報告

検出結果を種別ごとに提示する。修正案は「人間が決めること」として選択肢を示すに留める。

| 種別 | 検出内容 | 想定される次の手 |

## 適用記録の proposal

このスキルが `business_rules.md` を書き換えた場合、その適用を proposal として記録する。**proposal がケイパビリティの変更履歴である**という原則に従うため、判断を変えないリファクタリングであっても、本文が動いた事実と落とした情報の行き先を残す。

### 生成の要否

| 今回動かしたもの | 記録 |
|---|---|
| フェーズ B で本文を書き換えた / フェーズ C の (a) で ID を動かした | **生成する** |
| フェーズ A の構造整形だけ | 生成するかどうかを確認する（既定は生成しない。ID も本文も変わっていないため） |
| 何も適用していない（D のみ、または全て見送り） | 生成しない |

### ファイルと構造

**ファイル名:** `miko/<capability>/proposals/YYYY-MM-DD-refine-br-<kebab-case-topic>.md`（topic は今回の主題。例: `format-and-vocabulary`）

**冒頭に必ず付記する**（`/miko.quick-catchup` の事後 proposal と同じ扱い。実装スキルに再適用させないため）:

> このプロポーザルは `/miko.refine-br` による **適用済み** のリファクタリング記録です。実装対象ではありません。

**構造:** `.miko/examples/proposal.md` に準ずる。リファクタリング記録固有の書き方:

- **背景・動機**: 現在のガイド基準へ合わせ込んだこと、通したフェーズ
- **ビジネスルールの変更**: 本文を書き換えたルールを「改訂」として旧→新で並べる。フェーズ C の (a) で分割・統合したものは「新設」「廃止」として書く。**判断は変えていない旨を各項に明記する**（条件・閾値・対象範囲・除外規則が同一であること）
- **検討・却下した代替案**: **フェーズ B で本文から落とした経緯・理由・却下した代替案をここに移す。** 「これを知らないと将来間違えそう」というものは必ず残す（落として捨てるのではなく、書く場所を本文から proposal に移すのがガイドの前提）
- **影響範囲**: フェーズ C で動かした ID の対応表（旧 ID → 新 ID、欠番になった ID）、更新した `harae.md` の指摘番号、新 ID を併記した proposal のパス
- **他ケイパビリティへの影響**: フェーズ D の検出結果は書かない（未対応の検出であり、この proposal の変更内容ではない）。完了報告で扱う

**祓え検証セクションは作らない。** ルール体系の検証が必要な変更（フェーズ C の (b) ルート）は、そちらの適用前 proposal で `/miko.harae` に掛ける。

生成後、パスを提示して確認を取る。
