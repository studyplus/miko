## 入力

```text
$ARGUMENTS
```

入力の形式: `<capability_name>` または `<capability_name> <proposal_path>`

- 例: `/miko.refine-br order_management`（リファクタリング提案を起草する）
- 例: `/miko.refine-br order_management miko/order_management/proposals/2026-07-29-refine-br-format-and-vocabulary.md`（起草済みの提案を適用する）

**`miko/<capability>/business_rules.md` が存在しない場合はエラー:**

> ⛩️  `miko/<capability>/business_rules.md` が見つかりません。
> 既存コードがある場合は `/miko.catchup <capability>`、新規ケイパビリティの場合は `/miko.new-cap <capability>` で先に business_rules.md をお作りくださいませ。

## このスキルの役割

既存の `business_rules.md` をリファクタリングする。ここでのリファクタリングとは、**ドメインの判断を変えない書き直しと再配置** である。

`.miko/guides/business_rules_guide.md` は「既存 `business_rules.md` の構造と、proposal が触らない既存ルールの本文には、ユーザーからの明示的な移行依頼がない限り手を入れない」と定めている。**このスキルの実行が、その明示的な移行依頼にあたる。**

### 変更はすべて proposal にする

miko の原則では、ケイパビリティの変更はプロポーザルで行い、プロポーザルが変更履歴になる。判断を変えないリファクタリングも例外にしない。

- **起草モードは `business_rules.md` を一切変更しない。** 各フェーズで主さまに確認を取るが、その確認はセッション上に消えるものであり、記録ではない。確認済みの変更は proposal に書き出して初めて記録になる
- したがって、**途中のゲートで打ち切っても BR は無傷** である。次回はフェーズを指定せず最初からやり直せばよい。フェーズ単位の再開機構は持たない
- 適用は proposal を渡した「適用モード」でのみ行う。起草と適用の間に `/miko.harae` を挟める

### モード判定

| 入力 | モード |
|---|---|
| ケイパビリティ名のみ | **起草モード** — フェーズ A〜D を通し、リファクタリング提案を生成する。BR は変更しない |
| ケイパビリティ名 + proposal パス | **適用モード** — 起草済みの提案を BR に適用し、`harae.md` の参照を付け替える |

### 判断が変わる変更は扱わない

| 変更の性質 | 担当 |
|---|---|
| 判断を変えない書き直し・再配置（語彙・粒度・構造・配置） | **このスキル** |
| 判断そのものの変更（ルールの新設、条件・閾値・対象範囲の変更、廃止） | `/miko.propose` |
| 実装とルールの乖離（未実装なのに制約と断定している、既知の実装漏れがルールとして残っている） | `/miko.propose`（このスキルは検出して報告するだけ） |

本文から判断が消える変更（ルールごとの削除、対象範囲の縮小、閾値の変更）は、見た目が「本文の整理」であってもこのスキルでは行わない。検出して完了報告に回す。

### フェーズ構成（起草モード）

| フェーズ | やること | ルール ID | proposal への出力 |
|---|---|---|---|
| **A** | フォーマット最新化（ポリシーセクション新設、2.1/2.2 分割、採番コメント、状態遷移の欠如） | 不変 | 構造の変更 |
| **B** | 安全な言い換え（語彙規律違反、経緯の混入、実装トレース・ADR 混入） | 不変 | ルールの改訂 / 検討・却下した代替案（本文から落とす経緯の移設先） |
| **C** | 分割・統合（新規 ID 採番を伴うもの） | **変わる** | ルールの新設・廃止 / 参照の付け替え表 |
| **D** | ケイパビリティ横断チェック（境界・重複・同音異義語・帰属） | 不変 | **書かない**（変更ではなく検出。完了報告で扱う） |

各フェーズの末尾に確認ゲートを置く。**どのゲートでも打ち切ってよい。** 打ち切る場合は、それまでに確認できた内容で proposal を書き出すか、破棄して終えるかを選べる。

### 保証すること

- 起草モードは `business_rules.md`・`harae.md`・`proposals/` の既存ファイルを変更しない
- フェーズ A・B・D はルール ID を動かさない。ID を動かすのはフェーズ C だけ
- ID を動かす場合、参照元（`harae.md` の指摘・`proposals/`）の対応付けは **必ず人間が決める**。対応表を機械的に確定させない
- ルールの判断（条件・閾値・対象範囲・除外規則）は変えない
- 本文から落とした情報は捨てない。経緯・却下した代替案は proposal に、ADR は `high_level_design.md` に移す

# 起草モード

## 0. 入力検証と資料の読み込み

`$ARGUMENTS` の先頭ワードをケイパビリティ名としてスネークケースに正規化する。

以下を読み込む。

**指示書（必須）:**
- `.miko/guides/business_rules_guide.md` — ドキュメント構造、客観性テスト、紙運用テスト、語彙規律、粒度基準、カタログの書き方
- `.miko/guides/tone_guide.md` — 対話スタイル。**このファイルの口調・絵文字・出力言語ルールに従うこと**

**実例（目標とする構造）:**
- `.miko/examples/business_rules.md`
- `.miko/examples/proposal.md` — 生成する proposal の構造

**対象:**
- `miko/<capability>/business_rules.md` — 全文
- `miko/<capability>/high_level_design.md` — あれば（ADR の移設先の確認用）
- `miko/<capability>/harae.md` — あれば（フェーズ C で参照する指摘）
- `miko/<capability>/proposals/` — ファイル名一覧（フェーズ C で参照を辿る起点）
- `miko/glossary.md` — あれば（マスター値の対訳、用語衝突の確認用）

## 1. 現状診断

対象ファイルを診断し、フェーズごとの作業量を提示する。

| 項目 | 判定 |
|---|---|
| ビジネスポリシーセクション | 有 / 無 |
| 2.1 / 2.2 分割 | 済 / 未 |
| 状態遷移セクション | 有 / 不要 / 無（状態を持つ概念あり） |
| 各カテゴリの `<!-- last: -->` | カテゴリごとに 有 / 無 |
| ルール総数・カテゴリ数 | 数値 |

診断結果と、これから通すフェーズを提示してから作業に入る。フェーズ A の対象がすべて揃っている場合は「対応不要」と報告し、フェーズ B へ進むかを確認する。

## フェーズ A: フォーマット最新化

ルール ID・本文・タグを変えずに、ファイルの構造を現行ガイドの `## ドキュメント構造` に揃える案を作る。

### A-1. ドメイン / システムの判定（2.1 / 2.2 が未分割の場合）

`business_rules_guide.md` の「紙運用」テスト（そのルールは、システムが存在しない世界でも意味として成立するか）をカタログの全ルールに適用する。

**判定は、ルール本文に書かれている内容だけを見て行う。** 背景セクション・実装マッピング・proposal に書かれた「なぜこのルールが必要になったか」という理由は判定に使わない。ルールが生まれた理由が技術的（非同期処理、外部システムとの整合性回復など）であっても、ルールの中身が紙運用で成立するなら、それはドメインビジネスルールである。

- 良い判定: 「投稿者名は正規の経路以外からは参照されないよう秘匿する」— 実現手段が暗号化であっても、「誰に開示するか」という約束自体は紙の鍵付き書庫でも成立する → ドメイン
- 避けるべき誤り: 実装マッピングに「平文を残さないため」と書かれていることを根拠に、上記をシステム側へ分類すること。**ルールが必要になった理由（why）と、ルールの中身の分類（what）を混同しない**

**カテゴリ単位で判定する:**
- カテゴリ内の全ルールが同じ判定に収まる場合、カテゴリごと 2.1 または 2.2 に配置する
- 混在する場合は、ガイドの原則（同一カテゴリはどちらか一方に置く）に従い、カテゴリを 2.1 側・2.2 側に分けて両方に配置する。**プレフィックスも番号も変えない。** カテゴリ見出しは両側で同じ日本語名・同じプレフィックスを使う（`#### 申込管理（APP）` が 2.1 と 2.2 の双方に現れてよい）

**要確認の扱い:** 本文の内容だけを見ても判定が割れるルールは、自動で決めずに「要確認」として挙げ、A-4 で個別に判断を仰ぐ。両論を意図的に作り出さない。実データでは、本当に割れるのはケイパビリティあたり数件に収まる。

### A-2. ビジネスポリシー候補の検出（ポリシーセクションが無い場合）

`business_rules_guide.md` の「客観性」テスト（任意のケースで客観的に判定できるか。できないなら方針）を、背景セクションの記述と各ルールの前提になっている考え方に適用する。

- 価値判断・優先順位の表明が既存ルールや背景に埋没しているものを `POL-{連番}` の候補として抽出する
- **無理に見つけない。** 目安はケイパビリティあたり 3〜5 個。候補が薄い場合は、セクション新設を今回は見送るかどうかを A-4 で確認する
- ポリシー候補の抽出元（どのルール・どの背景記述から読み取ったか）を必ず併記する。抽出元のルール本文は変更しない（ポリシーはルールの上位ではなく、整合する別の層である）

### A-3. 状態遷移セクションの欠如（状態を持つ概念がある場合）

状態を持つ概念があるのに状態遷移セクションがない場合、内部矛盾の検証指摘を繰り返し生む原因になる。以下の条件でのみ下書きを提示する。

- 図示する遷移は、**既存のルール本文・操作の定義・glossary の対訳から読み取れるものだけ**にする。読み取れない遷移を推測で足さない
- 読み取れない遷移・条件は、図に含めず「要確認」として列挙する（空欄のまま人間に渡す）
- 状態名は生値ではなく `business_rules_guide.md` の語彙規律に従い「ビジネス用語（値）」の併記で書く

下書きを作らずに「欠如を報告するだけ」に留める選択も提示する。

### A-4. 【確認 A】

以下をまとめて提示し、承認を得る。

- 2.1 / 2.2 の配置案（カテゴリ単位の判定結果、混在カテゴリの分割方針）
- 要確認ルールの一覧。**「A（ドメイン）と B（システム）どちらの解釈も成り立ちますが、どちらに寄せますか」の形で 1 件ずつ**判断を仰ぐ。まとめて一括承認を求めない
- ビジネスポリシー新設案（候補と抽出元、または「候補なし」）
- 状態遷移の下書き（作った場合）と、その要確認箇所
- `<!-- last: -->` の追加箇所

フィードバックがあれば反映して再提示する。承認された内容は proposal の「構造の変更」セクションの草案として持ち越す。**この時点でファイルは書き換えない。**

### A-5. 【ゲート A】

確認済みの件数を報告し、以下を選んでもらう。

- フェーズ B へ進む
- ここで打ち切り、確認済みの内容で proposal を書き出す
- 破棄して終える

## フェーズ B: 安全な言い換え

ルール ID を変えずに、本文の書きっぷりを現行基準に合わせる案を作る。**判断は変えない。**

### B-1. 禊による本文審査（サブエージェント）

カタログの既存ルール本文を、`.miko/guides/misogi_guide.md` の審査役に掛ける。起草者ではない審査役にテキストだけで判定させるため、サブエージェント（Agent ツール）を起動する。

サブエージェントに渡す情報:
- `.miko/guides/misogi_guide.md` のパス — 「このファイルを読み、指示に正確に従え」と指示する
- ケイパビリティ名
- 審査対象のルール本文（ルール ID と `[制約]`/`[導出]` タグ付き）

**会話の経緯・ユーザーの発言・背景セクション・実装マッピングは渡さない。** 文脈が審査を汚染する。特に「なぜこのルールが必要になったか」を渡すと、語彙・粒度の判定がその理由に引きずられる。

ルールが 30 本を超える場合はカテゴリ単位でグループ分けし、サブエージェントを並列で起動する。

### B-2. 審査結果の裁定

審査結果をこのスキルのスコープに振り分ける。

| 違反種別 | このスキルでの扱い |
|---|---|
| 語彙逸脱（クラス名・メソッド名・API パラメータ名・enum の生値・実現手段の固有名） | **フェーズ B**: 書き換え案を作る |
| 粒度過大のうち、経緯・理由の記述を落とせば収まるもの | **フェーズ B**: 経緯を落とした本文案を作る（結論だけ残す）。**落とす経緯は proposal の「検討・却下した代替案」へ移す** |
| 粒度過大のうち、独立した判断が同居しているもの | **フェーズ C** の分解候補へ送る |
| 実装トレース / UI 仕様 / 技術仕様の**混入**（除いてもルールに判断が残る） | **フェーズ B**: 混入部分の除去案を作る。UI の表示状態の列挙・データフォーマット等は `high_level_design.md` への移設候補として示す |
| 実装トレース等が**ルールの全体**（除くとルールが消える） | **扱わない**。ルールごとの削除は判断の変更にあたる。完了報告で `/miko.propose` に誘導 |
| 要望の言い換え / 判定テスト不合格 | **扱わない**。同上 |
| 判定不能 | **扱わない**。完了報告で列挙 |

**語彙の言い換え先:**
- enum の生値・マスター値は `glossary.md` か状態遷移セクションの対訳を使う。対訳がない場合は言い換えを確定させず、要確認として提示する（glossary への追加は `/miko.propose` の領分）
- 他ケイパビリティで別概念を指す語は、glossary で立てた一意な別名に置き換える。別名がまだない場合は要確認として提示する
- 実装マッピングに書くべき語（クラス名等）が本文から消える場合、実装マッピングに同等の記載があるかを確認する。無ければ実装マッピングへの追記も proposal に含める

### B-3. ADR 混入の検出（メインセッション）

技術選定の決定・意図・トレードオフの議論がルール本文や実装マッピングに埋め込まれていないかを確認する。該当する場合は、`high_level_design.md` の「設計上の特徴」への移設案として proposal に載せる（`business_rules_guide.md` の注記に従い、ADR は BR に書かない）。

`high_level_design.md` が存在しない場合は、移設先がないため BR からの除去は提案せず、検出の報告に留める。

### B-4. 【確認 B】1 ルールずつの差分提示

**一括承認を求めない。** ルール 1 本ごとに以下を提示し、採用・修正・見送りを選んでもらう。

```
### {ルールID}

- 現在: {現在の本文}
- 案: {書き換え後の本文}
- 直した点: 語彙逸脱（`Xxx#method` → 業務語）/ 経緯の除去 / 仕様の除外
- 落とす経緯: {本文から外す経緯。proposal に移す}（該当する場合）
- 判断の変化: なし（条件・閾値・対象範囲・除外規則は同一）
```

「判断の変化: なし」と言えない案は提示しない。判断が動くなら `/miko.propose` の領分である。

件数が多い場合はカテゴリ単位で区切って提示してよいが、採用の可否は 1 ルールずつ受け取る。**本文から落とす経緯はその場で破棄せず、ルール ID ごとに控える**（proposal の「検討・却下した代替案」に移すため）。

### B-5. 【ゲート B】

採用件数・見送り件数、フェーズ C に送った分解候補の件数を報告し、以下を選んでもらう。

- フェーズ C へ進む
- ここで打ち切り、確認済みの内容で proposal を書き出す
- 破棄して終える

## フェーズ C: 分割・統合

新規 ID の採番を伴う変更を扱う。**ID が動くのはこのフェーズだけ。** ここでも適用はせず、proposal に載せる。

### C-1. 候補の確定

- フェーズ B から送られた分解候補（独立した判断が同居しており、経緯を落としても解けないもの）
- 1 ファイル内で同じ判断が複数の ID に分かれている統合候補

いずれも「判断の中身は変えず、境界を引き直すだけ」であることを確認する。分割の結果としてどちらかの判断が変わるなら、それは `/miko.propose` の領分として外す。

### C-2. 参照調査（サブエージェント）

対象ルール ID を参照している `harae.md` の指摘と `proposals/` を洗い出し、対応表の下書きを作る。サブエージェント（Agent ツール）を起動する。

サブエージェントに渡す情報:
- `.claude/skills/miko.refine-br/guides/reference_impact_guide.md` のパス — 「このファイルを読み、指示に正確に従え」と指示する
- ケイパビリティ名
- 対象ルール ID の一覧と、分割・統合の案（新 ID 案を含む）

対象ルールが多い場合は ID をグループ分けして並列に起動する。

### C-3. 【確認 C】変更案と対応表

候補ごとに以下を提示する。

- 分割・統合の案（分割後の本文、新 ID 案。統合の場合は統合先 ID と欠番になる旧 ID）
- 参照元の一覧（`harae.md` の指摘番号とステータス、proposal のパス）
- 対応表の下書き（旧 ID → 新 ID）

**曖昧サイン**（`reference_impact_guide.md` が検出する）に該当した行は、対応表を自動で埋めず「この対応は主さまが個別にお決めください」と明示して **1 件ずつ** 判断を仰ぐ。

1. 指摘が本文の一部（サブ条件・特定の側面）だけを参照している
2. 指摘が「そのルールが独立 ID として存在すること自体」を論点にしている（統合すると指摘の前提が壊れる）
3. 1 つの旧 ID に対する参照が harae 指摘・proposal 合わせて 5 件以上ある

決められない行は「保留」として proposal に `要確認` のまま残す。**保留が残っている proposal は、適用モードで必ず再確認する。**

### C-4. 【ゲート C】

分割・統合の件数、保留にした対応表の行数を報告し、以下を選んでもらう。

- フェーズ D へ進む
- ここで打ち切り、確認済みの内容で proposal を書き出す
- 破棄して終える

---

## フェーズ D: ケイパビリティ横断チェック

**検出のみ。** 検出結果は proposal には書かない（このリファクタリングの変更内容ではないため）。完了報告で提示し、対処は `/miko.propose` に委ねる。

### D-1. 調査（サブエージェント）

`miko/*/business_rules.md` が存在する他のケイパビリティを対象に、サブエージェント（Agent ツール）を起動して調査する。対象が多い場合は数ケイパビリティずつに分けて並列に起動する。

サブエージェントに渡す情報:
- `.claude/skills/miko.refine-br/guides/cross_capability_check_guide.md` のパス — 「このファイルを読み、指示に正確に従え」と指示する
- 対象ケイパビリティ名
- 調査を担当する他ケイパビリティ名の一覧

**会話の経緯・ユーザーの発言は渡さない。** ガイドのパスと調査対象の指定だけを渡す。

### D-2. 結果の整理

検出結果を種別ごとに整理する。修正案は「人間が決めること」として選択肢を示すに留める。

| 種別 | 検出内容 | 想定される次の手 |
|---|---|---|
| 境界の片側欠落 | A が B に依存していると書いているが、B 側の「関連ケイパビリティとの境界」に A の記載がない | 欠けている側への追記（`/miko.propose`） |
| 判断の重複定義 | 同じ判断が複数の BR に別 ID で書かれている（一字一句同一の例もある） | どちらに寄せるかの決定（`/miko.propose`。片方にしか検証履歴がない場合は harae.md の扱いも決める） |
| 同音異義語・衝突語 | glossary の見出し語と衝突する語、複数ケイパビリティで別概念を指す語 | 別名を立てるリネーム（`/miko.propose`） |
| 帰属が怪しいルール | 隣接ケイパビリティに置く方が自然に見えるルール | 移動の可否（`/miko.propose` の横断プロポーザル） |

境界の片側欠落は、依存の事実が依存先に書かれていないことで本番事故につながった実例がある。検出したものは深刻度を添えて報告する。

### D-3. 【ゲート D】

検出件数を報告し、proposal の生成へ進む。

## proposal の生成

確認済みの内容を 1 本の proposal にまとめる。**ここまでで `business_rules.md` は一度も変更していない。**

確認済みの変更が何もない場合（全フェーズで見送り、または D しか実施していない）は生成せず、完了報告だけを行う。

**ファイル名:** `miko/<capability>/proposals/YYYY-MM-DD-refine-br-<kebab-case-topic>.md`（topic は今回の主題。例: `format-and-vocabulary`）

**冒頭に必ず付記する:**

> このプロポーザルは `/miko.refine-br` が起草したリファクタリング提案です。ドメインの判断は変更しません。
> 適用は `/miko.refine-br <capability> <このファイルのパス>` で行ってください（構造の変更・参照の付け替えを含むため、`/miko.quick-impl` では扱えません）。

**構造:** `.miko/examples/proposal.md` に準ずる。リファクタリング提案固有のセクション:

- **背景・動機**: 現在のガイド基準へ合わせ込むこと、通したフェーズ、判断は変えないこと
- **構造の変更**（フェーズ A）: ビジネスポリシーセクションの新設内容（POL の本文と抽出元）、2.1 / 2.2 の配置表（カテゴリ → 配置先）、`<!-- last: -->` の追加箇所、状態遷移セクションの下書きと要確認箇所
- **ビジネスルールの変更**:
  - **改訂**（フェーズ B）— ルール ID ごとに 現在 → 変更後 を並べ、直した点（語彙 / 経緯 / 仕様）を添える。**各項に判断が同一である旨を明記する**
  - **新設・廃止**（フェーズ C）— 分割後の新 ID と本文、欠番にする旧 ID。統合の場合は統合先と欠番
- **参照の付け替え**（フェーズ C）: 対応表（旧 ID → 新 ID）。行ごとに参照元（`harae.md` の指摘番号 / proposal のパス）を書く。保留の行は `要確認` と明記する。付け替えの方針も書く — `harae.md` は ID を置き換え、`proposals/` は履歴なので旧 ID を残して新 ID を併記する（`ORD-04（現 ORD-12 / ORD-13）`）
- **検討・却下した代替案**: **フェーズ B で本文から落とした経緯・理由・却下した代替案をここに移す。** 落として捨てるのではなく、書く場所を本文から proposal に移すのがガイドの前提
- **影響範囲**: 「変更しないもの」に、判断（条件・閾値・対象範囲・除外規則）が同一である旨を書く
- **他ケイパビリティへの影響**: 書かない。フェーズ D の検出は変更内容ではないため、完了報告で扱う

**祓え検証セクションは作らない。** `/miko.harae <capability> <proposal>` を掛けた場合に、そちらが追記する。

生成後の案内:

> ⛩️  リファクタリング提案をお納めいたしました。
> ルールの分割・統合を含む場合は `/miko.harae <capability> <proposal>` での検証をお勧めいたします。
> 適用は `/miko.refine-br <capability> <proposal>` でお進みくださいませ。

## 完了報告（起草モード）

以下をサマリーテーブルで提示する。

| フェーズ | 確認済みの件数 | proposal への反映 |
|---|---|---|
| A | 新設セクション / 分割したカテゴリ数 / 採番コメント追加数 | 構造の変更 |
| B | 書き換えるルール数 / 見送り数 / HLD へ移設する件数 | ルールの改訂 |
| C | 分割・統合数 / 保留にした対応表の行数 | 新設・廃止、参照の付け替え |
| D | 検出件数（種別別） | — |

**残したもの:**

- フェーズ C で保留にした対応表の行（誰が何を決める必要があるか）
- フェーズ D で検出したもの（種別・深刻度・想定される次の手）
- ガイドの構造そのものに起因する読みにくさ（混在カテゴリを 2.1 / 2.2 に分けた結果、同じカテゴリがファイル内の離れた 2 箇所に現れる等）。このスキルでは変えない

**`/miko.propose` に回すもの（別枠で明示する）:**

- 実装とルールの乖離（本文が「〜しなければならない」と断定しているのに実装マッピングが「（未実装）」、既知の実装漏れがルールとして残っている等）
- ルールごとの削除が必要なもの（実装トレースが本文の全体を占めている、要望の言い換えである等）
- 語彙の言い換え先が glossary にないもの（別名・対訳の新設が必要）
- フェーズ D の検出

> ⛩️  これらは「実装するか、諦めるか」の判断が必要でございます。書き直しでは片付きませんので、`/miko.propose <capability>` でお進みくださいませ。

**BR は未変更である旨を明記する。** 適用するまで `business_rules.md` は一切変わっていない。

# 適用モード

proposal パスが渡された場合。起草済みの提案を `business_rules.md` に適用する。

## 1. 検証

- proposal を読み込む。冒頭に `/miko.refine-br` の付記がない場合はエラーとして中止する:
  > ⛩️  このプロポーザルは `/miko.refine-br` が起草したものではないようです。
  > 通常のプロポーザルは `/miko.quick-impl <proposal>` でお進みくださいませ。
- 既に適用済みの印（`> 適用済み: YYYY-MM-DD`）がある場合はエラーとして中止する
- `business_rules.md` を読み、proposal が前提としているルール ID・カテゴリ構成が現状と一致するかを確認する。起草後に BR が動いている場合は、食い違いを提示して中止する（起草からやり直してもらう）

## 2. 保留行の確認

「参照の付け替え」に `要確認` の行が残っている場合、適用前に 1 件ずつ判断を仰ぐ。**保留のまま適用しない。**

## 3. 適用

proposal の内容を順に適用する。

- **構造の変更**: ビジネスポリシーセクションは「背景」の直後・「状態遷移」の前に置き、末尾に `<!-- last: POL-XX -->` を付ける。2.1 / 2.2 に配置し直し、各カテゴリの末尾に `<!-- last: -->` を付ける。カテゴリ内のルールの記述順は元のまま保つ
- **ルールの改訂**: 本文を差し替える。ID・タグは変えない
- **新設・廃止**: 新 ID を採番し、旧 ID は欠番にする（番号は詰めない）。統合は統合先に本文を寄せ、統合された旧 ID を欠番にする
- **HLD への移設**: `high_level_design.md` の「設計上の特徴」に追記する
- **参照の付け替え**:
  - `harae.md`（生きている指摘）— 「関連ルール」欄の ID を対応表どおりに書き換える。指摘の本文・ステータスは変えない
  - `proposals/`（変更履歴）— 旧 ID は消さず、新 ID を併記する（`ORD-04（現 ORD-12 / ORD-13）`）。本文の判断記述は変えない
- **適用した proposal**: 冒頭の付記の下に `> 適用済み: YYYY-MM-DD` を追記する

## 4. 【確認】適用結果の提示

変更したファイルと差分の要点（ルール ID 単位）を提示し、確認を取る。

## 5. 完了報告（適用モード）

- 適用した proposal のパス
- 変更したファイル（`business_rules.md` / `high_level_design.md` / `harae.md` / 参照を併記した `proposals/`）
- 適用したルール ID（改訂 / 新設 / 廃止・欠番）
- 付け替えた参照の件数

ルールの分割・統合を適用した場合は、`/miko.harae <capability>` での再検証を案内する。
